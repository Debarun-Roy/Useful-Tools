# Java auth starter

Build with `mvn -B -ntp clean verify`. Source release is Java 17; Servlet 6.1 requires a compatible container. Target container is Tomcat 11.0.26. Execution versions are recorded by UsefulTools B5 certification, not inferred from compiler release. This is a standalone application, not a plugin for UsefulTools.

Read auth-spec.json, environment.example.json and SECURITY.md before startup. Set every required named environment variable. AUTH_DATABASE means an absolute SQLite file path or PostgreSQL JDBC URL `jdbc:postgresql://HOST:PORT/DATABASE?sslmode=verify-full`; only loopback PostgreSQL may explicitly use sslmode=disable. Credentials are separate environment values. Examples are placeholders; there is no seeded account. For a new empty owned database, set the named initialize variable to the exact string true. Afterwards set false. Initialization creates version 1 only, never migrates or resets an existing application. Existing version must be 1. SQLite database directory and PostgreSQL public schema must be restricted to the service operator. Use backups and a reviewed migration process for future versions.

Deploy target/*.war in Tomcat, configure an HTTPS connector and a trusted certificate. Exact origins in auth-spec.json must match browser Origin values (no trailing slash). Default mode is production and rejects insecure requests. Explicit development mode permits HTTP only from loopback and only loopback HTTP origins. Forwarded protocol/host/address headers are ignored. TLS must terminate at the servlet connector; reverse proxy deployments need a separate reviewed trust configuration. Session cookie path matches deployed context. Ship the generated META-INF/context.xml or equivalently configure maxActiveSessions=4096, pathname empty and SameSite=Lax at the container. Do not enable session persistence, URL rewriting or clustering without a reviewed design. Do not expose auth-spec.json or database files through the web root.

Client sequence using a cookie jar: GET api/auth/csrf-token; retain the cookie and csrfToken. POST api/auth/register with username/password, trusted Origin and X-CSRF-Token, receiving 201 without login. POST api/auth/login with the same headers/cookie receives 200 and rotates session/CSRF. GET api/auth/csrf-token again. Read api/auth/session and, when selected, api/user/profile. PATCH profile with displayName and/or preferences using the new token. POST logout with {} clears the cookie and invalidates the server session; replaying the old cookie cannot authenticate. OpenAPI describes paths/statuses and schemas. All unsafe calls require application/json, including logout.

When CAPTCHA is enabled, obtain a reCAPTCHA v3 token using the public site key in your own frontend, action register or login, and send captchaToken with credentials. Store only the secret in its named server environment variable. The server calls the fixed Google endpoint, checks action, hostname, score and age, and fails closed. No frontend success boolean is trusted. Disabled CAPTCHA is explicit in the spec. Never use real provider calls in automated tests; Java constructor dependencies permit a bounded synthetic transport in an external test harness.

The included Maven tests check hashing, parser bounds, configuration failure and bounded throttling. They do not certify HTTP, browser cookies, PostgreSQL or CAPTCHA. The repository B5 verification runs those separately against real exported WARs. Independent security review is still required before external release.
