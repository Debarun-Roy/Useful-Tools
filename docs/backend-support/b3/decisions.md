# B3 contract and capability decisions

B3 uses schemaVersion 0.3.0, independently pinned migration-0.3.0-b3, view-0.3.0-b3 and evaluator-0.3.0-b3 templates; evaluator ruleset schema-rules-0.3.0. Embedded executable schemas use the unchanged B2 0.2.0 snapshot contract. Evaluator uses a separate bounded diagnostic model that admits empty PKs, unknown logical types and inert expression-default text. The historical 0.1.0 and released 0.2.0 contracts and schema bundle bytes remain frozen.

All modules share POST generate/export, transport, authorization, strict decoder, concurrency and shared rate budget. No new execution/evaluation endpoint. Canonical input includes module/template/ruleset, target, both normalized snapshots, explicit rename maps, destructive acknowledgement and external-dependency-review choice. Report exports regenerate and compare preview digest just like SQL. Malformed/unprocessable input is rejected; completed evaluation with diagnostic errors succeeds as a report-only result and never implies executable-schema eligibility.

Migration executable subset: append nullable columns; append columns with supported constant literal defaults (required columns need nonnull constants); add ordinary nonunique indexes; explicit same-stable-ID table and column database renames. Current-timestamp/expression additions, reordered columns, table additions/removals, column removals, all existing type/options/nullability/default/key/FK/check changes, index removals/changes and unique-index creation block executable output. Nullable-to-required and unique-index changes explicitly require manual data validation/backfill or duplicate prechecks; they are not supported merely by acknowledgement. Multi-table cycles remain unsupported. Explicit rename records must exactly match before/after database names and stable IDs; missing/conflicting/stale maps block. A rename target occupied in the before model blocks conservatively. No inferred identity rename or SQLite rebuild.

Migration planning is deterministic: all table renames in snapshot order, followed by each table's column renames/appended columns and added indexes in snapshot order. Every unsupported difference blocks the complete executable bundle, including mixed plans. Response findings include Added/Changed/Removed/Manual summaries. No-op plans are explicit. Before and after each retain 100 tables/1,000 columns; combined columns capped at 1,000 plus global request/node/depth limits. Comparisons use ID maps, not unbounded cross products. The fixed temporary runner table name ut_b3_guard is reserved for migration input tables (MIGRATION_INTERNAL_NAME_COLLISION), preventing temporary-object shadowing without changing the released B2 name validator.

Migration execution is operator-run only. Bundled runner performs fail-on-precheck, changes and postchecks in one transaction: SQLite PRAGMA foreign_keys=ON confirmed before BEGIN IMMEDIATE; PostgreSQL transaction with ACCESS EXCLUSIVE locks on all modeled tables and ON_ERROR_STOP. A maintenance window and reviewed external dependencies are mandatory. Prechecks cover modeled table/column counts, ordered names, rendered types, nullability and expected ordinary-index presence; external views/triggers and PostgreSQL inheritance/partition dependencies are rejected. They do not prove arbitrary customer schemas or fully compare all CHECK/default/FK/collation semantics; operator review of the supplied before snapshot remains required. The generated guard INSERT with CHECK makes a failed predicate abort; SELECT output alone is never treated as enforcement. Postchecks verify after shape. Failures roll back the transaction. No per-statement commit.

Down SQL exists only for index/rename-only reversible plans; it is a reverse-order schema reversal, not a backup. A plan adding columns has no automatic down.sql because dropping them may destroy later writes. Backup/restore guidance is explicit. Data preservation is asserted only for the synthetic tested subset; no arbitrary production migration safety claim.

Views: one explicit source and up to eight sequential INNER/LEFT equijoins, unique aliases including self joins; explicit projected column references or COUNT/SUM/AVG/MIN/MAX; COUNT(*) uses a null aggregate argument and differs from COUNT(column). WHERE permits bounded AND/OR/NOT, typed comparisons eq/ne/lt/le/gt/ge and IS NULL/IS NOT NULL. Equality to null is rejected; persisted parameters/raw SQL/subqueries/functions/materialized views are unsupported. SUM/AVG require numeric columns; JSON aggregate/comparison forms are unsupported. Every nonaggregate projection in an aggregate/grouped query must be grouped. All sources/aliases/columns and emitted-name collisions are checked; literals reuse B2 typed validation/escaping. Referenced tables must already exist; no table creation is included.

Evaluator rules: missing PK, invalid FK target, incompatible FK types, identical-index redundancy (ordered column IDs plus unique flag), nullable explicit unique/business keys, unsafe/unsupported defaults, unsupported logical types/options, advisory snake_case naming (or disabled). No guessed business meaning, index-prefix heuristic, quality score, normalization claim or performance guarantee. Findings have stable rule IDs, severity, safe numeric contract paths, fixed explanation/correction and generation-block scope. Invalid prerequisite references/types produce bounded checks-not-run records rather than cascades. Findings are sorted deterministically, capped at 100 with explicit truncation. Unsafe expression text remains inert and is never SQL-rendered.

Shared limits, no-store, metadata-only privacy, text rendering, abort plus revision/request guards and timezone-independent ZIP metadata remain unchanged. Flat safe paths are extended to multiple nonempty filename segments for before.schema.json/after.schema.json; traversal, consecutive dots, directories, drives and symlinks remain prohibited. B3 manifests reuse the noncircular canonical-core/payload hashing domains; historical B2 output is unchanged.

Sources: [SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html), [PostgreSQL 17 ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html), [SQLite CREATE VIEW](https://www.sqlite.org/lang_createview.html), [SQLite SELECT grouping rules](https://www.sqlite.org/lang_select.html), [SQLite aggregates](https://www.sqlite.org/lang_aggfunc.html). Both actual target engines remain mandatory execution gates.
