# B6 decisions
Python generator schema/template 0.6.0 is separate from Java0.5.0; shared HTTP contract remains 0.5.0 including JSESSIONID and anonymous session200. Frozen B0–B5 contracts/templates and byte pins are mandatory. Python fields are project, pythonModule and pythonVersion3.14, not Maven/package/container fields. Fixed source only; operator data serialized inertly. Common policy validation reuses the B5 validator through an explicit inert Java adapter; emitted Python is separately rendered. AuthOpenApi stays unchanged and emits the same selected language-neutral routes/schemas.

Runtime candidate pins verified with clean install/pip check: Python3.14.3, FastAPI0.135.1, Starlette1.6.0, Pydantic2.13.5, Uvicorn0.41.0, Starsessions2.2.1, redis-py6.4.0, argon2-cffi25.1.0, psycopg3.3.6, HTTPX0.28.1. All transitive runtime/test pins included in generated requirements. These are B0 candidates checked for compatibility, not a claim of latest versions. TestClient emits a Starlette HTTPX deprecation warning; actual socket/browser tests remain the gate, no warning suppression or automatic dependency upgrade.

Starsessions RedisStore retained as maintained adapter; automatic SessionMiddleware not used because its documented last-writer-wins save can resurrect revoked state. Explicit lifecycle operations hold a bounded striped lock per presented ID through the handler, read live state before mutation, delete old ID on rotation, and never save at response completion. Process-local active registry caps4096 and revokes old namespace on restart. Every process boot has random Redis key prefix; no KEYS/FLUSHDB/shared cleanup. One worker only. Real Redis TTL and deletion supplemented by idle/absolute clock bounds; no memory fallback. Hash work2, DB workers8, Redis connections16 and supported Uvicorn concurrency64 bound execution.

Windows live Redis provisioning uses community redis-windows upstream-source Redis8.2.10 Cygwin portable build, checksum92d9bdde87ed52bf859a677e5197d8ac855ba78d9940d457881723ae960df429. This is a real Redis process, not fakeredis and not an official native Redis support claim. No installed WSL distribution/Docker available. Disposable loopback only, protected mode, no persistence, maxmemory64MiB/noeviction, own subprocess and SHUTDOWN NOSAVE; no service installation. Production operators supply independently managed Redis/TLS/ACLs; Windows test provisioning is not production approval. Actual PING/clean exit and session TTL/rotation/race diagnostic passed; full acceptance pending.

HTTP precedence follows parity-matrix.md. Strict manual bounded parser precedes framework convenience; framework coercion/default422 is excluded. Cookie-only same-origin, root deployment only; supplied root_path rejected. Supported launcher has direct TLS, proxy_headersFalse, no access logs, one worker. Profile identity comes only from session; values bound to SQL; no arbitrary schema migrations. Startup new empty DB only, version1; DB errors sanitized. Blocking hash/DB work reserves slots before submitting and holds them until underlying work finishes, including coroutine cancellation.

UI uses separate mounted target editors to preserve valid/invalid Java/Python drafts and revision/abort identity. B5 tests no longer assert Python unavailable because B6 explicitly authorizes it; they still require Java target/version/template and run the full Java matrix. Shared client treats HTTP header names case-insensitively, retaining exact required values, statuses, fields and errors. No released template bytes changed for these test/catalog additions.

The first full run hit Windows commit/paging exhaustion launching a Java test JVM. B6 verification now explicitly caps every child JVM via JAVA_TOOL_OPTIONS=-Xms32m -Xmx512m, recorded in evidence; this changes disposable verification process sizing, not generated artifacts or application security bounds. The external fillSessions setup (4096 sequential real Redis writes) gets a 60-second harness deadline instead of the normal 10-second control deadline. Actual HTTP/store deadlines and all 4096/capacity/failure/recovery assertions are unchanged.
