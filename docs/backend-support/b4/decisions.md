# B4 design and compatibility decisions

Scope BS06 only: Java generates one-table Python ETL bundles, never executes them or accepts datasets. New contract 0.4.0/template etl-0.4.0-b4; embedded destination schema is the frozen B2 0.2.0 snapshot. Old 0.1.0 ETL samples remain historical validation input, not implicitly converted. Source/target/mappings/policies/runtime variable names participate in the canonical request digest. Existing endpoints, authorization, bounds and transient packaging remain unchanged.

Runtime: Python 3.14.3, stdlib sqlite3 and pinned psycopg 3.3.6 binary for PostgreSQL 17.11; Windows is the tested host. Exact transitive requirements will be recorded after a clean installation. Official references: https://docs.python.org/3.14/library/csv.html , https://docs.python.org/3.14/library/json.html , https://docs.python.org/3.14/library/decimal.html , https://www.psycopg.org/psycopg3/docs/basic/install.html , https://www.psycopg.org/psycopg3/docs/basic/transactions.html . Python CSV reader returns text; JSON parse_float=Decimal avoids a binary-float intermediate. No arbitrary transformation code/import/eval is allowed.

Parsing: CSV explicit UTF-8 or UTF-8-with-BOM, comma/semicolon/tab delimiter, double-quote quoting and doubled quote escaping, no escapechar, strict reader, newline preservation, required first header, blank physical records skipped, multiline quoted values count as one logical record. Duplicate headers and parser corruption are fatal; trustworthy width errors are row rejects. JSON is a top-level array of objects, strict UTF-8/BOM policy, duplicate keys/nonstandard numbers rejected, Decimal numbers preserved. The implementation snapshots finite source bytes before processing: CSV at most 16 MiB, JSON at most 2 MiB, 100,000 records, 100 fields, 4,096-character fields, 64 KiB record, nesting 32. JSON is deliberately finite in-memory parsing, not an unbounded stream or JSON Lines. Source is immutable; identity is SHA-256 of full bytes and runtime rechecks before committing batches.

Mappings: unique source field and target stable-column references. Ordered trim/lower/upper text transforms followed by an explicit final cast, ISO date, DMY date or ISO timestamp conversion. Case conversion only for text/varchar; date formats only for date, timestamp only for timestamp. Missing, explicit null and empty-after-transformation policies are separate: reject/null/default; empty additionally keep for text. Whitespace is not automatically null. Default means omit the column from INSERT/UPDATE and use the destination default for inserts; explicit null is a bound SQL NULL. Integer/bigint enforce 32/64-bit ranges, bool accepts true/false or 0/1 only, decimals use Decimal with precision/scale enforcement and no rounding, dates use exact declared formats, timestamps require offsets or explicit UTC-naive policy. Named zones are unsupported. JSON target values are bounded valid JSON. SQLite NUMERIC remains approximate storage; PostgreSQL NUMERIC preserves validated precision/scale.

Destination: existing database/table only, finite names/types/nullability/key compatibility checks before writes. SQLite opens mode=rw and confirms foreign_keys before transactions. PostgreSQL requires explicit environment JSON with host/port/dbname/user/password/sslmode; inherited PG settings are cleared in the child process, errors are sanitized, source values are parameterized. No DB creation/migration. Upsert requires a mapped nonnullable explicit primary/unique key and mapped non-key update columns. Repeated source keys apply in order; last accepted value wins for explicitly updated columns. Unmapped/default-omitted columns are preserved on conflict. No INSERT OR REPLACE, append fallback, or unmeasured inserted/updated split. Triggers and concurrent writers limit replay side-effect guarantees.

Transactions: batch size 1–1,000. Strict validates the batch before writes, rolls back its current batch on row/constraint failure, exits nonzero and retains earlier commits. Continue mode uses row savepoints for database integrity errors; connection/parser/checkpoint/infrastructure errors remain fatal. Counters distinguish read, validated, committed, rejected and uncommitted; read = committed + rejected + uncommitted. Committed counts successful row operations, including repeated-key upserts, not distinct rows. Reject reports contain record number, mapping path and constant reason only; bounded append reports fail explicitly before exceeding their configured cap. Reports may contain replay duplicates after a crash; checkpoints do not claim exactly-once file writes.

Checkpoint state machine: acquire single-runner locks; validate immutable source/spec/template/destination identity; load checkpoint only with --resume; parse/re-read and skip last durable logical record; validate batch; transaction/savepoints; commit; append sanitized reject entries; atomically write same-directory temporary checkpoint with flush/fsync then replace. Never checkpoint before commit. External checkpoints record format version, identities, last logical record, counters and completion state. A commit acknowledged before checkpoint can replay. Upsert resume is deterministic for mapped values, with trigger/side-effect caveats; insert resume always requires --acknowledge-insert-replay/manual reconciliation. Ambiguous commit outcomes are fatal, never presumed rolled back. OS file locks prevent simultaneous use of one checkpoint; SQLite also locks the database's ETL lock file; PostgreSQL uses a table-scoped advisory lock. The canonical checkpoint location and immutable source are operator prerequisites. Truncated/malformed/changed-input checkpoints fail closed. No exactly-once claim.

Dry run parses/transforms/validates without database connection, write transaction, checkpoint/lock changes, or source mutation; no credentials needed. Optional explicit reject output is separate local diagnostics. It does not prove database constraints. Exit codes: 0 clean, 2 completed with rejects, 3 invalid configuration/input/checkpoint, 4 strict batch or fatal/interrupted failure. Sanitized JSON summaries contain counters/status/reason, never source values, SQL parameters, paths or credentials.

Bundle: fixed etl.py plus helper if needed, etl.spec.json, configuration.example.json with environment names only, exact requirements.txt, README.md, synthetic example.csv/example.json, verify.py and manifest.json. Fixed template code reads configuration as data. User-provided text is not spliced into Python. Actual HTTP ZIP programs must install/run in fresh environments for CSV/JSON × SQLite/PostgreSQL, with external subprocess fault injection at commit/checkpoint/reject boundaries.
