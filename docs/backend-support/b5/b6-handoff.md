# B6 handoff — conditional on B5 certification

B6 is not started. Proceed only after docs/backend-support/b5/sprint-pass.md and evidence.json show every G1–G10 PASS against unchanged inputs, and a user explicitly authorizes B6. Preserve the dirty repository, earlier contracts/templates and reports. No commit, deployment or production database work is authorized by this handoff.

Framework-neutral sources are contracts/backend-support/v0.5.0/api-contract.md and parity-fixtures.json, plus each actual Java export's openapi.json. The generator schema describes Java-specific project configuration; B6 needs its own independently versioned Python template/target without reinterpreting frozen B0 REST drafts or changing B5 bytes. Shared endpoint family: register/login/logout/session/csrf-token and optional profile GET/PATCH. Required core includes persistence, hashing, session auth, Origin/CSRF and throttling; profile depends on core.

Contract decisions: ASCII username 3–32 lowercased without trimming; unchanged passwords default 15–128 code points, 512 UTF-8 bytes maximum, no composition rules. Registration 201 does not log in. Login 200 establishes identity and rotates both opaque session ID and CSRF; already authenticated login is conflict. Missing/wrong/unknown-user credentials use the documented validation/generic login statuses. Baseline user role/UUID identity is server generated. Profile is session-owned and changes only displayName/preferences; preferences replaces the map. Unknown/internal/owner fields are rejected. DB uniqueness and transaction rollback must be verified on both targets.

Anonymous CSRF bootstrap never authenticates. Stored-token absence fails closed. Every unsafe request requires exact trusted Origin. Existing sessions require CSRF for logout; absent/expired logout remains Origin-protected and returns 204 while clearing the cookie. Cookies are HttpOnly/Secure/Lax/context-scoped in production, cookie-only, no Domain. Idle/absolute expiry, logout and restart revoke server state. No cross-origin support or trusted forwarded headers are included. Distributed session/throttle behavior is not claimed.

CAPTCHA uses reCAPTCHA v3 directly in register/login; enabled mode validates success, expected action/hostname, score, freshness and types. Missing secret is startup failure; provider failure never disables verification. Off mode is explicit. Test the same on/off matrices with synthetic provider responses and no real Google traffic. Runtime secrets come through named environment variables, never generator inputs or emitted frontend code.

Reuse parity fixtures as language-neutral request/response scenarios, including positive flow and negative field/Origin/CSRF/JSON/media cases. Expand Python parity to all executed B5 session, rate, persistence, provider and HTTPS browser cases; do not substitute compilation or mocked service calls for runtime HTTP. Java-specific HttpSession/changeSessionId, Servlet filter dispatch/PATCH, Tomcat cookie/manager configuration, JDBC transaction behavior and Password4j PHC parameters require deliberate Python equivalents rather than mechanical copying.

Remaining deployment gates: independent security review before external auth-template release, verified TLS/connector limits, minimally privileged DB credentials and controlled schema/files, secret delivery and redacted infrastructure logs, backup/migration and dependency-update procedures, and a separate approved design before multi-instance deployment. B5 self-review and local certification are not hosted-CI or production approval. Exact verified versions, limitations, commands, hashes and remaining failures belong to the final B5 report/evidence.
